## 二、职责边界

### 2.1 Grok CLI：工程负责人

负责：

1. 读取现有代码、数据库结构、路由和采集脚本；
2. 设计向后兼容的数据迁移；
3. 建立候选清单 JSON Schema、CSV 字段和校验器；
4. 编写国内史料候选导入、去重、分级和报告脚本；
5. 实现 `/domestic`、国内来源页、检索筛选和调档进度页；
6. 编写测试和运行验证；
7. 对 MiniMax 输出做机器校验，不替代史料判断。

禁止：

- 独立决定史料是否为一手材料；
- 根据模糊标题虚构档号、日期、页码或版权状态；
- 修改或提交 SQLite、扫描件、压缩包；
- 未经复核把候选记录直接发布到前台；
- 与 MiniMax 同时修改同一文件。

### 2.2 MiniMax CLI：史料研究负责人

负责：

1. 从权威机构入口普查国内一手史料；
2. 生成首批 200 条候选记录；
3. 判断形成者、载体类型、原始性候选等级和相关度；
4. 为九个关键事件建立国内史料证据清单；
5. 提取核心人物、机构、地点、事件和检索词异写；
6. 复核 Grok 生成的栏目文案、字段解释和证据卡片；
7. 标记不确定、需登录、需馆内访问、需线下调档或版权待核的项目。

禁止：

- 直接修改 `app.py`、`platforms.py`、迁移脚本或数据库；
- 把搜索结果摘要当成档案原文；
- 猜测档号、馆藏号、页码、永久链接；
- 将回忆录、论文和新闻转载标为 L0—L3；
- 输出无法追溯来源的“事实性结论”。

### 2.3 Codex：协调与验收

负责：

1. 固定任务契约和目录；
2. 启动两个 CLI 的阶段任务；
3. 监督文件边界和 Git 状态；
4. 对候选 URL、字段完整性、重复项和权利风险做终审；
5. 运行测试、审查差异并合并；
6. 只有验收通过的记录才能进入公开前台。

### 3.1 外部模型安全边界

Grok 和 MiniMax 是外部模型服务。项目采用“公开任务包 → 外部审查 → 本地映射”的隔离方式：

1. Codex 在本地读取仓库、数据库结构和项目文档；
2. Codex 只把通用字段、公开定义、模拟记录和公开检索问题整理成脱敏任务包；
3. 外部 CLI 只在临时目录运行，不把项目仓库设为工作目录；
4. 外部模型不得读取、索引或写入项目目录；
5. 外部输出先进入临时审查区，由 Codex 检查后再手工映射到正式 Schema、脚本和文档；
6. 真实档案内容、未公开候选、原始文件和本地数据库永不发送给外部模型；
7. 公开网页研究可以由外部模型执行，但输入只能包含公开检索目标，输出必须保留公开 URL 和访问日期。

这不是关闭安全检查，而是固定一条可长期执行的最小披露边界。任何需要外部模型直接读取仓库的任务，改由 Codex 本地完成。

## 六、互审机制

每阶段执行两轮：

1. **生产轮**：主责 CLI 生成成果；
2. **反方轮**：另一 CLI只做审查，输出问题清单。

具体安排：

| 成果 | 生产者 | 审查者 |
|---|---|---|
| 数据契约与校验器 | Grok | MiniMax |
| 来源注册表 | MiniMax | Grok |
| 200 条候选 | MiniMax | Grok |
| 数据迁移与导入器 | Grok | MiniMax |
| 页面实现 | Grok | MiniMax |
| 事件证据摘要 | MiniMax | Grok |

审查输出统一分级：

- `BLOCKER`：虚构来源、权利风险、数据破坏、无法复核；
- `MAJOR`：分级错误、重复、日期或形成者冲突；
- `MINOR`：格式、文案、别名和展示问题；
- `NOTE`：后续研究建议。

只有 `BLOCKER=0` 且 `MAJOR` 全部关闭，才能进入下一阶段。
